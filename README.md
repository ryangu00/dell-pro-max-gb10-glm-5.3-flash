# GLM-5.3-Flash on Dell Pro Max with GB10 ×2 —— 一次判死的完整实录(失败案例篇)

> 我们花了一整天在双机上部署测试 GLM-5.3-Flash,最终判定**不换代**。
> 失败案例的避坑价值不比成功低:这本书告诉你我们撞了什么、怎么诊断、以及为什么"能跑起来"不等于"能用"。
> (注:判死针对"本地双机跑此权重";云端 API 不受这些本地稳定性问题影响——但另有一个输出泄漏风险,见质量结论节。)

## 硬件与尝试的栈

| 项 | 规格 |
|---|---|
| 机器 | Dell Pro Max with GB10 ×2(sm_121,128GB 统一内存 each) |
| 栈 A | vLLM TP2 双机(同本系列 DSV4F 篇形态) |
| 栈 B | EXL3(exllamav3)双机配方(`glm-5.3-flash-exl3-2x-spark`) |
| 结论 | **判死:不上生产**。同期基线(DeepSeek V4 Flash Vision Exp 双机)全面更稳 |

## 撞了什么(按时间线)

1. **初始化就不稳**:vLLM 栈(同本系列 DSV4F 篇镜像线)冷启动 5 次仅 1 次成功进入服务态,其余卡死在权重加载/编译阶段。sm_121 上该模型的算子路径成熟度不足。
2. **120K 长上下文确定性崩**:与本系列 Flash-Next 篇的 95K 死线同类——标称长上下文,实际在此栈某长度阈值确定性崩。再次验证:**长上下文安全线必须逐模型逐栈实测**。
3. **单机加载 wedge(#109 类)**:大权重加载把统一内存打穿,机器假死。击穿组合(**仅单机加载场景需要,且属高风险系统调参,做完必须回滚**):
   ```bash
   sudo fallocate -l 48G /swap-tmp && sudo mkswap /swap-tmp && sudo swapon /swap-tmp
   sudo sysctl vm.watermark_scale_factor=200
   # 加载完成后回滚:
   sudo swapoff /swap-tmp && sudo rm /swap-tmp && sudo sysctl vm.watermark_scale_factor=10
   ```
   外加降低 GPU 内存占用比;**双机 TP2 分片加载不需要这套**(每机只吃一半权重)。
4. **serving 参数被 install 脚本抹掉**:调好的参数重跑 install 后消失——必须直写 env 文件的 `${VAR:=}` 默认值行(同本系列 DSV4F 篇坑 #6,我们在这个模型上第一次付出学费)。
5. **镜像 digest-pin 在离线搬运时失效**:`docker save | load` 丢 repo digest(同 DSV4F 篇坑 #9,也是在这轮学的)。

## 质量结论(为什么"能跑"也判死)

跑通的窗口里我们完成了六维评测(代码生成/调试/中文/长逻辑/agentic/数学,各维 0-100 自建尺):**仅代码生成一项胜出(41.5,基线同维更低)**,其余维度落后或持平;而稳定性(init 1/5、120K 崩)在生产语境是一票否决。
同权重的云端 API 版另有一个值得知道的风险:我们 2026-09 经某第三方 API 聚合网关调用时,多次观测到思考流以英文泄漏进 content 字段(是否复现取决于网关与服务端版本,请自验:检查 content 是否含 `<think>` 或成段英文推理)——如果你在任何地方用这个系列的模型做面向用户的输出,给 thinking 加 budget clamp 并检查 content 里有没有 `<think>` 残留。

## 这本书的可复用结论

- **"部署成功"的标准不是服务 200,是:init 成功率+长上下文安全线+并发稳态三关全过**。我们的三关流程:冷启动 ×5 计成功率 → 长度阶梯实测(方法见本系列 Flash-Next 篇)→ 并发稳态(6 路混合:2 短问答+2 代码生成+2 中长文,30 分钟,通过标准=零 worker 崩溃且聚合吞吐不趋零)。
- 新模型上双机前,先单机小量化版本探路,确认算子路径基本成熟再上 TP2——TP2 的故障面是单机的平方。
- 判死不删档:权重与配置留位(存储便宜),引擎迭代后重测的成本远低于重新下载配置。
